# 07. 回答までの処理とレイテンシ

目標: **質問から回答の最初の 1 文字までの時間（TTFT）を 10 秒以内**（p95）。

回答までの処理（[03](03-knowledge-units-and-teacher.md) §4.2）は 5〜6 段ある。毎回すべてを順番に LLM で処理すると 10 秒を超えうるため、処理の組み立て方を 3 案で比較し、段階的に採用する方針を定める。

> 本書の時間はいずれも経験上の目安であり、実測はチャット API の実装時に行う（§6）。

## 1. 処理の段（共通）

| 段 | 内容 | 主な処理 |
|---|---|---|
| ① 質問の分解 | 依頼の種類、条件（必須・希望）、検索語 | LLM |
| ② 検索 | 全文検索・ベクトル検索・知識カード検索 | 埋め込み（Vertex AI）＋ DB |
| ③ 候補の選定・理由付け | 検索結果から使うものを選び、理由を付ける | LLM |
| ④ 根拠の取得 | 選んだ候補の原文・ページ | DB |
| ⑤ 回答の作成 | 根拠付きの回答をストリーミング | LLM |
| ⑥ 根拠の検証 | 引用が本文に実在するか、ページ番号が合うか | DB（文字列照合） |

## 2. 案 A: 当初案（各段を順番に実行）

```
① 分解(LLM) → ② 検索 → ③ 選定(LLM) → ④ 根拠 → ⑤ 回答(LLM) → ⑥ 検証 → 表示
```

各段を独立した処理として順番に実行する。LLM が道具を自由に呼ぶ方式（エージェント型）も、実質的にはこの形（道具を 1 回呼ぶごとに LLM の往復が 1 回増える）になる。

| 段 | 目安 |
|---|---|
| ① 分解 | 1〜3 秒 |
| ② 検索 | 0.2〜0.5 秒 |
| ③ 選定 | 1〜3 秒 |
| ④ 根拠 | 0.1 秒未満 |
| ⑤ 回答の TTFT | 1〜4 秒 |
| ⑥ 検証を回答の前に置く場合 | 回答全体の生成時間（数秒〜数十秒） |
| **TTFT 合計** | **3.5〜10 秒（⑥を前に置くと 10 秒超）** |

- 長所: 実装・デバッグが最も単純。段ごとの入出力を記録すれば再現できる。
- 短所: LLM の往復が 3 回直列。混雑時やコールドスタート時に 10 秒を超える。⑥を回答の前に置くと目標は達成できない。

## 3. 案 B: 整理案（呼び出しを減らす。処理は順番のまま）

```
計画(軽量 LLM, ①と③の検索条件をまとめて) → ② 検索 → ④ 根拠 → ⑤ 回答(選定も回答の中で) → ⑥ 検証(回答後)
     約 1〜1.5 秒                          約 0.3〜0.5 秒        TTFT 約 1〜3 秒
```

並列化はせず、**LLM の呼び出し回数を減らす** ことと、**重い処理を入稿時に済ませる** ことで速くする。

1. **回答前の LLM 呼び出しを 1 回にする。** ①の分解と、③に必要な検索条件の生成を、軽量モデルの 1 回の「計画」呼び出しにまとめる。候補の選定・理由付けは、回答を書くモデルに上位 20 件ほどの根拠を渡して回答の中で行わせる。
2. **簡単な質問は計画を飛ばす。** 「3 章を要約して」「○○ってどういう意味？」などは規則か非常に軽い判定で振り分け、計画の呼び出しを省く。
3. **根拠の検証は回答の後に行い、回答を止めない。** 回答はそのまま流し、生成が終わったら引用を照合する（DB 上の文字列比較で数ミリ秒〜）。画面では出典を「確認中 → 確認済み」と後から確定させ、照合に失敗した引用は差し替えるか取り消す。
4. **入力を短く、または使い回す。** 本ごとに変わらない部分（先生の設定、コードレビュー用の原則カード一覧など）はプロンプトキャッシュに載せる。根拠は必要な分だけ渡す（チャンク 20 件程度。章の全文は「詳しく」と言われたときだけ）。
5. **重い処理は入稿時に済ませる。** 階層要約・知識カード・人物の名寄せ・営業時間の構造化などは入稿時に作る設計なので、質問時は「検索して 1 回答える」だけで済む。
6. **インフラ側の対策。** Cloud Run の最小インスタンス数を 1 以上にしてコールドスタートを避ける（現在のイメージは約 730MB）。DB 接続はプールして使い回す。Cloud Run・Cloud SQL・Vertex AI は同じリージョンに置く（Claude を東京以外で呼ぶ場合は 1 回あたり 0.1〜0.2 秒程度増える見込み）。
7. **進み具合をすぐ画面に流す。** 回答の前に「『戦争と平和』の第 2 巻を調べています…」などを 1 秒以内に表示する。TTFT の数字は変わらないが、体感の待ち時間は大きく減る。

| 段 | 目安 |
|---|---|
| 計画（省略可） | 1〜1.5 秒 |
| ② 検索（全文・ベクトル・カードを順番に） | 0.3〜0.5 秒 |
| ④ 根拠 | 0.1 秒未満 |
| ⑤ 回答の TTFT | 1〜3 秒 |
| **TTFT 合計** | **約 2.5〜5 秒** |

- 長所: 処理は順番のままで、案 A とほぼ同じ単純さで実装・デバッグできる。速度向上の大半はこの案で得られる。
- 短所: 計画の呼び出しと検索の待ち時間はそのまま足し算になる。

## 4. 案 C: 並列案（待ち時間を重ねる）

案 B に加えて、待ち時間を重ねる。

```
                    ┌─ 計画(軽量 LLM) ──┐
質問 ──┬────────────┤                   ├─ 追加検索(差分) ─┐
       │            └───────────────────┘                  │
       └─ 元の質問文で先行検索（全文 ∥ ベクトル ∥ カード）───┴─ 統合 → ⑤ 回答（ストリーミング）
                                                                         └─ ⑥ 引用が出るたびに検証
```

1. 計画の結果を待たずに、元の質問文で検索を同時に始めておく。計画結果による追加検索は差分だけ行う。
2. 全文検索・ベクトル検索・知識カードの検索を同時に投げる。
3. 回答を流しながら、引用が出た時点でその都度照合する（Claude の引用機能（根拠の位置を構造化して返す）を使えば照合はさらに単純になる。引用機能は Vertex AI でも使えることを確認済み。ただし出力形式の固定（structured outputs）とは併用できない）。

| 段 | 目安 |
|---|---|
| 計画 ∥ 先行検索 | 1〜1.5 秒（長い方） |
| 追加検索（差分） | 0〜0.3 秒 |
| ⑤ 回答の TTFT | 1〜3 秒 |
| **TTFT 合計** | **約 2〜4.5 秒** |

- 長所: 最も速い。
- 短所（**実装・デバッグが複雑になる**）:
  - **失敗の組み合わせが増える。** 先行検索だけ失敗した、計画だけ時間切れになった、などの部分的な失敗それぞれに振る舞いを決める必要がある。
  - **実行順が毎回変わる。** 結果の統合順や時間切れの有無で回答の材料が変わり、同じ質問でも再現しにくい。
  - **取り消し処理が要る。** ユーザーが途中で質問を取り消した場合に、走っている並列処理をすべて止める必要がある。
  - **テストが書きにくい。** 時間に依存する挙動（どちらが先に終わるか）のテストは不安定になりやすい。
  - **流しながらの検証** は、画面側の状態管理（未確定の引用の表示・差し替え）も複雑にする。
  - 得られる短縮は **案 B に対して 0.5〜1 秒程度** の見込み。

## 5. 比較と方針

| | 案 A: 当初案 | 案 B: 整理案 | 案 C: 並列案 |
|---|---|---|---|
| TTFT の目安 | 3.5〜10 秒（混雑時は超過） | 約 2.5〜5 秒 | 約 2〜4.5 秒 |
| LLM の往復（回答前） | 2 回 | 0〜1 回 | 0〜1 回（検索と重ねる） |
| 実装の複雑さ | 低 | 低〜中 | 高 |
| デバッグ・再現性 | 容易 | 容易 | 難（実行順・時間切れに依存） |
| テスト | 容易 | 容易 | 難（時間依存） |
| 10 秒目標 | 危うい | 余裕あり | 余裕あり |

**方針: 案 B で実装し、実測で必要と分かった箇所だけ案 C の手法を足す。**

- 速度向上の大半は「LLM 呼び出しの削減」「プロンプトキャッシュ」「入稿時の前処理」「最小インスタンス」で得られ、どれも並列化を必要としない。
- 案 C の手法は効果に対して複雑さの増分が大きいので、計測で p95 が目標を超える場合にだけ、効果の大きい順に足す。
  1. 検索（全文・ベクトル・カード）の同時実行。DB と埋め込みの呼び出しだけで閉じ、失敗時は「その検索結果なしで続行」と決めやすい。複雑さの増分が最も小さい。
  2. 計画と先行検索の同時実行。
  3. 流しながらの検証（画面側の作り込みが要るので最後）。

### 並列化を入れる場合の約束事（複雑さを抑えるため）

- **並列にする箇所を 1 か所（検索の段）に閉じ込める。** 回答の生成・検証の流れには持ち込まない。
- **並列を切れるようにする。** 設定（例: `SENSEI_PARALLEL=0`）で順番実行に切り替えられるようにし、デバッグや不具合の切り分けは順番実行で行う。
- **統合の順序を決め打ちにする。** 終わった順ではなく、決まった順（全文 → ベクトル → カード）で結果を統合し、同じ入力なら同じ材料になるようにする。
- **各処理に時間切れを設定し、失敗時の振る舞いを 1 通りに決める**（その結果なしで続行し、ログに残す）。
- **段ごとの入出力と所要時間を記録する。** 質問 ID ごとに計画・検索結果・渡した根拠・回答を保存し、後から同じ材料で回答を再生成（再現）できるようにする。

## 6. 計測

チャット API の最初の版から、段ごとの所要時間を Cloud Trace に記録する（計画・埋め込み・各検索・根拠の取得・回答の TTFT・回答の完了・検証）。代表的な質問セットをジャンル別（コードレビュー・料理・旅行・文学）に用意し、p50 / p95 を測る。案 C の手法を足すかどうかは、この計測結果で判断する。

## 7. 注意点

- **モデルの選び方**: 回答に大きなモデルを使うほど TTFT と生成速度は遅くなる。計画は軽量モデル、回答は品質と速度の釣り合いで選び、実測して決める。
- **コードレビューは入力が大きい**（原則カード一覧で数万トークン）。プロンプトキャッシュが効かないと TTFT が延びるため、キャッシュの当たり具合も計測項目に入れる。
- **エージェント型（LLM が道具を自由に何度も呼ぶ方式）** は、通常の質問には使わない。固定の流れで答えられない複雑な質問の逃げ道として残し、その場合は進み具合の表示で待ち時間を補う。
