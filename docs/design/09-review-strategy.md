# 09. レビューの考え方

LLM が作る知識カード・要約・文脈ヘッダは量が多く（MVP1 の 12 冊でカード約 1,800 枚）、人が 1 件ずつ見て直すのは現実的でない。本書では、人が全件を見ることを前提にせず、どこで誰が何を確かめるかを定める。

[03](03-knowledge-units-and-teacher.md) §5 の [7.5] Review（「1 冊 1 時間程度の人手確認」）と、同 §8 の未決事項 4（カードの人手確認を入れるか）を本書で置き換える。

## 1. 基本方針: 人はレコードではなく仕組みを直す

LLM の誤りは 1 件ずつばらばらに起きるのではなく、同じ原因で同じ種類の誤りが繰り返し起きる（コード例の良い例・悪い例を逆に判定する、人物の別名を統合し損ねる、など）。1 件ずつ直しても次の本で同じことが起きるが、プロンプトや規則を直せば全部の本でまとめて直る。

| | 従来の考え方 | 本書の方針 |
|---|---|---|
| 人が見るもの | 全レコード | **例外・抜き取り・ボットの振る舞い** |
| 直す対象 | 個々のレコード | **生成の仕組み**（プロンプト・語彙・規則）。直したら該当する段だけ再実行する |
| 合否の単位 | レコード | **本（版）単位で受け入れるかどうか** |
| 個別の修正 | 普通の作業 | 例外。重要なものだけ（§5） |

段ごとの成果物とキャッシュ（[02](02-ingestion-mvp-validation.md)）があるため、プロンプトを直したときは影響する段から後ろだけを再実行できる。

## 2. 誤りの種類ごとの見つけ方

人が見なくても見つけられる誤りは機械に任せる。

| 誤りの種類 | 例 | 見つける手段 | 人の出番 |
|---|---|---|---|
| **本に書いていないことを書く** | 原文と違う引用、存在しない引用、本文にない材料名 | **機械的な照合**（根拠ブロックの実在、引用文が原文に存在するか、値が本文にあるか）。[5.6] Unit validation | なし |
| 根拠と内容が合っていない | カードの主張が、示した根拠ブロックから言えない | **別の LLM による検証**（カードと根拠ブロックを渡し「根拠から言えるか」を判定） | 判定が割れたものだけ |
| 重要なものの取りこぼし | 章の主要な原則がカードにない、主要人物が欠けている | **網羅性の検査**（章ごとのカード数の偏り、階層要約に出てくる語がカードにあるか、目次のレシピ数とカード数の一致） | 偏りのある章だけ |
| 分類・属性の誤り | カテゴリ違い、別名統合の誤り | **抜き取り検査**（§3.2） | 1 冊 20〜30 件 |
| 影響の大きい誤り | ネタバレの位置（`revealed_at`）、営業時間・価格 | 種類を決めて**重点検査** | 対象の種類だけ全件 |
| 答え方の問題 | 正しいデータがあるのに引けない、口調、引用の見せ方 | **質問テスト**（§3.3） | 回答を読む |

最も危険な「本に書いていないことを書く」誤りは機械的な照合で検出できる。カードは必ず根拠ブロックを持ち、出典として見せるのは原文だけ、という [03](03-knowledge-units-and-teacher.md) の設計はこのためでもある。

LLM による検証のコストは小さい。カード 1 件と根拠で約 1,500 トークンとして、MVP1 の 12 冊（約 1,800 枚）で Haiku 5.5 なら約 $0.3、Sonnet 5.5 でも約 $6（[08](08-mvp1-corpus-and-ingest-cost.md) の単価）。

## 3. 人が見る 3 つのもの

### 3.1 例外キュー

自動の検査で引っかかったものを 1 本の列にまとめ、**影響の大きさ × 不確かさ** の順に並べる。人は上から順に、時間が許す範囲まで見る。

キューに入るもの:

- 機械的な照合で落ちたカード（[5.6]）
- LLM による検証で判定が割れたカード
- 網羅性に偏りがある章
- 表の読み取りの信頼度が低いもの（[03](03-knowledge-units-and-teacher.md) §6）
- Profile の確信度が低い特徴（[04](04-architecture-traits.md) §4）
- 入稿の QA で `review` になったもの（`qa.py`。目次との一致率、文字化け率など）
- 上書き（§5）の対象が再実行で消えた・大きく変わったもの
- 公開後の質問ログから見つかった問題（§7）

### 3.2 抜き取り検査

1 冊につき 20〜30 件を無作為に選び、誤り率を見積もる。目的は個々の誤りを直すことではなく、**その本（版）を受け入れてよいかを判定する** こと。

誤り率が基準を超えたら、レコードを直すのではなく原因を特定し、プロンプト・語彙・規則を直して該当する段を再実行する。

### 3.3 質問テスト（振る舞いの確認）

データの正しさより、利用者が体験するものを直接確かめる。

- 質問は目次・階層要約から自動生成し、人が少し足す。1 冊 20 問程度。
- 答えの決まる質問（「○○の初登場の章は」「この原則は何章か」）は自動採点する。
- 自由回答は人が読む。おかしな回答は「データの問題か、検索の問題か、回答の作り方の問題か」に切り分け、該当する段を直す。
- 質問セットはそのまま回帰テストになる。プロンプトを直したら全冊で回し直し、悪化していないかを確かめる。

検索だけの評価（`eval/progit-ja.yaml` の hit@k）は埋め込みしか使わないので、何度回してもほぼ無料。回答まで含めた評価は回答の LLM 代がかかる（[08](08-mvp1-corpus-and-ingest-cost.md) §6）。

## 4. 本ごとの受け入れ判定

すべての本に同じ手間はかけられないため、本の重要度で手間に差をつける。

| 本の区分 | 例外キュー | 抜き取り | 質問テスト | 1 冊あたりの目安 |
|---|---|---|---|---|
| 看板（よく使われる・宣伝に使う） | 全件 | 30 件 | 30 問、人が全部読む | 1〜2 時間 |
| 通常 | 上位だけ | 20 件 | 20 問。自動採点し、落ちたものだけ読む | 20〜30 分 |
| ロングテール | 致命的なものだけ | なし（仕組みが安定していれば） | 自動採点だけ | 5〜10 分 |

受け入れ基準を決めておき、判定は表を見て合否を付けるだけにする。基準の例（値は運用しながら調整する）:

| 項目 | 基準の例 |
|---|---|
| 機械的な照合の不合格 | 0 件（残っていれば公開しない） |
| 抜き取りの誤り率 | 5% 未満 |
| 質問テストの正答率（自動採点分） | 80% 以上 |
| 重点検査の対象（ネタバレ位置など） | 誤り 0 件 |

合否は版ごとに記録し、合格した版だけを公開・本番への登録の対象にする（[06](06-deployment-gcp.md)、書籍単位の昇格）。

## 5. 個別の修正は「上書き」として成果物に残す

それでも 1 件ずつ直したいもの（看板の本の重要なカードなど）は出てくる。これを DB で直接書き換えず、**上書き指示として成果物に別ファイルで保存** する。

```
books/{book_id}/v{version}/{extractor}/
  units.json        ← LLM が生成（再実行で作り直される）
  overrides.json    ← 人の修正・承認・却下（再実行しても残る）
```

- 登録（[6] Index）のときに「生成結果 + 上書き」を合成して DB に入れる。
- 再実行で生成結果が変わっても上書きは残る。上書きの対象が消えた、または内容が大きく変わった場合は例外キュー（§3.1）に出して人が確認する。
- 上書きの対象はカードの ID だけでなく、根拠ブロックなど再実行しても変わりにくい手掛かりでも引けるようにする（再実行でカードの ID が振り直されても対応が取れるように）。

修正が DB ではなく成果物にあるため、成果物から別の DB（本番など）に書籍単位で登録しても修正が一緒に入る。DB 上で直接直すと、その修正は DB にしか残らず、成果物から登録し直したときに消える。

## 6. 実装上の約束

本書の方針が成り立つために、LLM を使う段（[5] Enrich 以降）の実装で次を守る。

1. **LLM の出力は成果物として保存し、`manifest.json` のキャッシュに載せる。** キャッシュキーにはモデル名とプロンプトのバージョンを含める。直した段から後ろだけを再実行するため、また本番への登録で LLM を再実行しないため。
2. **[6] Index（DB への登録）では LLM を呼ばない。** 成果物と上書きを読んで書き込むだけにする。
3. **検査の結果（照合・LLM 検証・網羅性・抜き取り・質問テスト）も成果物として保存する。** 合否の根拠を版ごとに残すため。

## 7. 公開後も続くレビュー

公開前のレビューで全部は拾えない。[04](04-architecture-traits.md) §5 ③（実際の質問ログから見つける）をレビューの一部として位置づける。

- 回答への低評価、「本に書いていない」と答えた質問、検索結果が空だった質問を集める。
- それを例外キュー（§3.1）に流し込み、原因の段を直す。
- よく出る質問は質問テスト（§3.3）に追加する。

公開前のレビューは「明らかにおかしいものを出さない」ため、公開後のレビューは「実際の使われ方に合わせて良くしていく」ためのもの、と役割を分ける。

見つかった問題を直して本番に反映する手順（止める・個別に直す・仕組みを直す・原本が変わる）と、版の切り替え・巻き戻し・上書きの持ち越しは [10](10-post-release-fixes.md) で定める。

## 8. 作るもの

| 部品 | 内容 | 段 |
|---|---|---|
| 機械的な照合 | 根拠ブロックの実在、引用・値の本文照合（`search_key` で正規化して照合） | [5.6] |
| LLM による検証 | カード + 根拠ブロックを渡して判定。判定と理由を成果物に保存 | [5.6] |
| 網羅性の検査 | 章ごとのカード数、要約とカードの突き合わせ | [7] QA |
| 質問セットの生成と採点 | 目次・要約から質問を生成、答えの決まる質問の自動採点 | [7] QA |
| 例外キュー | 上記の結果を集め、影響 × 不確かさで並べる | [7.5] Review |
| 上書きの仕組み | `overrides.json` の合成、対象の追跡 | [6] Index |
| 受け入れ判定の記録 | 版ごとの合否と根拠 | [7.5] Review → [8] Publish |

最初は例外キューと受け入れ判定をファイル（JSON / Markdown のレポート）で出し、レビュー用の画面は運用が固まってから作る。

## 9. 未決事項

1. **受け入れ基準の値。** MVP1 の 12 冊で実際に回して決める。
2. **本の区分（看板・通常・ロングテール）を誰がどう決めるか。** 入稿時に人が指定するか、利用状況から自動で決めるか。
3. **LLM による検証に使うモデル。** 生成と同じモデルだと同じ誤りを見逃しやすい。別系統のモデル（生成が Opus なら検証は Sonnet、など）にするか。
