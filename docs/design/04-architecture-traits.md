# 04. 共通パイプラインと特徴パッケージ

[03](03-knowledge-units-and-teacher.md) で技術書・料理本・旅行雑誌・グルメ雑誌・文学作品を検討した結果、本の種類によって必要な処理は大きく異なることが分かった。
ただし違いが出る場所は限られている。本書では、**本の種類ごとに別々のパイプラインを作るのではなく、共通のパイプラインに本の特徴に応じた部品（特徴パッケージ）を差し込む** 構成を定める。

## 1. 何が共通で、何が違うのか

| 段 | 本による違い |
|---|---|
| 受付、構造化（章・節・ブロック・ページ番号）、チャンク分割、ベクトル化、階層要約、登録、QA の共通部分、根拠の検証、公開 | **共通** |
| 抽出 | 本の **レイアウト** で決まる（文字主体／雑誌の誌面／スキャン） |
| 知識カード（スキーマ・抽出プロンプト・検証規則・語彙） | 本の **内容** で決まる |
| 追加の処理段（位置計算、人物の名寄せ、号またぎの名寄せなど） | 内容で決まる。一部の本だけ |
| 先生の道具と口調 | 内容で決まる。一部を追加 |

違いは「抽出」と「知識カードまわり」に集中しており、流れの骨格は同じ。

## 2. 「タイプ」ではなく「特徴の組み合わせ」で捉える

レイアウトと内容は独立した軸である。同じ料理本でも文字主体の EPUB なら現行の抽出で足り、写真主体の誌面ならページ画像の読み取りが要る。小説でもスキャン PDF なら OCR が要る。

入稿時の判定（Profile 段）で本の **特徴（トレイト）の組み合わせ** を決め、特徴ごとに部品を有効にする。

```
『シャーロック・ホームズの冒険』
  レイアウト: text
  内容:      narrative + short_story_collection + mystery + method

『戦争と平和』
  レイアウト: text
  内容:      narrative + long_multi_volume + historical + many_characters + translated

ラーメンWalker
  レイアウト: magazine
  内容:      shop_menu + geo + opening_hours + periodical_series + has_ads

『リーダブルコード』
  レイアウト: text
  内容:      principles + code_examples
```

## 3. 特徴パッケージ

1 つの特徴が 1 つの部品セットになる。

```
特徴パッケージ = スキーマ + 抽出プロンプト + 検証規則 + 語彙
              + 追加の処理段 + 先生の道具・プロンプト断片
              + QA チェック + 評価用の質問
```

```yaml
# 例: traits/mystery.yaml（形式はイメージ）
trait: mystery
requires: [narrative]
schemas: [case, clue, method]
extract_prompts: [case_extraction.v1, method_extraction.v1]
validators: [quote_exists, clue_resolved_in_case]
stages: [narrative.foreshadowing_links]       # 伏線と回収の対応付け
teacher:
  tools: [list_units(case), list_units(method)]
  prompt_fragments: [spoiler_strict.v1]       # 犯人・トリックは最重要のネタバレ
qa_checks: [every_case_has_resolution]
eval_questions: eval/mystery/*.yaml
```

- パッケージは `requires` で他のパッケージに依存できる（mystery は narrative を前提とする）。
- 新しいジャンルへの対応は、パイプラインを丸ごと作ることではなく、**足りない特徴パッケージを足すこと**。
- 全部を最初からそろえる必要はない。共通の土台だけでもどの本も動くので、利用の多いもの・効果の大きいものから足す。

### 3.1 特徴の一覧（初期案）

**レイアウト**

| 特徴 | 内容 |
|---|---|
| `text` | 文字主体。テキスト層からの抽出（実装済み） |
| `magazine` | 多段組・写真・囲み記事。ページ画像を読ませる抽出が主 |
| `scanned` | テキスト層なし。OCR |
| `vertical` | 縦書き |
| `comic` | 漫画・絵本。コマ単位の画像読み取り |

**内容（実用・情報）**

| 特徴 | 内容 |
|---|---|
| `principles` | 原則・手法カード（技術書・ビジネス書） |
| `code_examples` | コード例の悪い例・良い例 |
| `recipes` | レシピカード、材料の正規化 |
| `spots` | エリア・スポットカード（旅行） |
| `shop_menu` | 店・メニューカード（グルメ） |
| `geo` | 位置・距離・所要時間 |
| `opening_hours` | 営業時間の構造化と営業中判定 |
| `periodical_series` | 雑誌のシリーズ・号またぎの名寄せ |
| `has_ads` | 広告ページの判定 |
| `procedures` | 手順カード（実用書） |

**内容（文学）**

| 特徴 | 例 | 必要になること |
|---|---|---|
| `narrative` | 小説全般 | 階層要約、人物・出来事・場所、別名の統合、`revealed_at` によるネタバレ回避 |
| `short_story_collection` | ホームズ、芥川の短編集 | 1 冊に複数作品。作品単位で要約・人物を分ける |
| `mystery` | クリスティ | 犯人・トリックは最重要のネタバレ。伏線と回収の対応 |
| `method` | ホームズの推理法 | 作品横断の方法カード（当てはめ用） |
| `nonlinear_time` | 回想・入れ子構造 | 「語られる順」と「物語の中の時間順」を別々に持つ |
| `drama` | シェイクスピア、チェーホフ | 台詞と話者、ト書きの区別。幕と場の構造 |
| `poetry` | 歌集、句集 | 1 作品が短い。形式・季語・技法。1 作ごとの鑑賞 |
| `classical` | 源氏物語 | 主語の省略、敬語による人物の特定、原文と現代語訳の対応付け |
| `historical` | 戦争と平和、司馬遼太郎 | 史実と創作の区別（史実は外部知識） |
| `epistolary` | 『あしながおじさん』 | 書き手と日付が構造になる |
| `unreliable_narrator` | 一人称の叙述トリック | 「語り手の主張」と「事実」を区別 |
| `series` | ホームズ全集、ハリー・ポッター | 複数冊をまたいだ人物・時系列・ネタバレ |
| `many_characters` / `long_multi_volume` | 戦争と平和 | 別名の大規模な統合、章ごとの並列抽出 |
| `translated` | 翻訳作品 | 翻訳ごとに別の本。引用はその翻訳の文章のまま |

## 4. 特徴の自動判別

| 特徴の種類 | 例 | 判別方法 | 自動化の見込み |
|---|---|---|---|
| レイアウト | text / magazine / scanned、段組、縦書き | テキスト層の有無、画像の面積比、文字配置の統計 | **ほぼ確実**（一部実装済み） |
| ジャンル | 料理、旅行、技術書、小説、外国文学 | 書誌情報（ISBN から日本の分類コード（C コード）や図書館分類を引く）＋目次と冒頭数ページを LLM で分類 | **高い** |
| 構造 | 短編集、戯曲、詩集、日記体、古典 | 目次と本文の見本を LLM で判定（話者ラベルが並ぶ → 戯曲、短い題付き作品が並ぶ → 詩集・短編集） | **高い〜中** |
| 内容の深い性質 | 時系列が入り組む、信用できない語り手、史実と創作の混在 | 全体を読まないと分からない。物語の抽出後に判明 | **中〜低** |

運用方針:

- **2 段階で判別する。**
  - 1 回目（Profile 段）: 入稿直後に安い材料（書誌情報・目次・冒頭）で判別する。
  - 2 回目（Narrative 段などの後）: 本文全体を処理した結果から特徴を追加する（出来事を並べたら回想が多いと分かった、など）。
- **確信度に応じて扱いを分ける。** 確信度の高い特徴は自動で適用し、低いものは入稿時に人がチェックリストで確認する（1 クリック程度）。
- **迷ったら有効にする。** 余計な特徴を有効にした損はコストの増加程度だが、必要な特徴が抜けるとその本でできることが減る。
- 有名作品は LLM が内容を知っているため判別しやすいが、新刊・無名作品には使えないので、本文からの判別を基本とする。

```jsonc
// Profile 段の出力（イメージ）
{
  "traits": [
    { "trait": "text", "confidence": 0.99, "source": "layout_stats", "applied": true },
    { "trait": "narrative", "confidence": 0.97, "source": "ccode+llm", "applied": true },
    { "trait": "short_story_collection", "confidence": 0.92, "source": "toc_llm", "applied": true },
    { "trait": "method", "confidence": 0.55, "source": "llm_proposal", "applied": false, "needs_review": true }
  ]
}
```

## 5. 使い方の設計

特徴の判別（この本はどういう本か）と、使い方の設計（この本で何ができるとうれしいか）は別の問題である。後者は人が考える部分が残るが、本ごとに毎回考える必要はない。3 段階で行う。

### ① 特徴ごとに一度だけ人が設計する（基本）

大半の使い方は本ごとではなく特徴ごとに決まる。人が一度設計すれば、その特徴を持つすべての本に自動で適用される。

| 特徴 | 定番の使い方 |
|---|---|
| `narrative` | あらすじ（粒度を選べる）、人物、関係、場面探し、テーマや象徴の解説、名言、作品の比較、読書会の論点出し |
| `mystery` | 伏線と回収、推理の手順の解説（ネタバレ厳格） |
| `drama` | この台詞の意図、登場人物ごとの台詞集 |
| `principles` | 原則の解説、自分の材料（コード・企画書）への当てはめ |
| `recipes` | 状況・季節・材料からの推薦、作り方 |

### ② 本ごとの独自の使い方は、LLM に提案させて人が承認する

ホームズの「方法論を仕事に当てはめる」のような使い方は本ごとに異なる。入稿時に LLM が全体の要約を読み、「この本で想定される使い方」と、そのために作るべきカード（例: 方法カード）を提案する。

| 本 | 提案される使い方の例 |
|---|---|
| 『孫子』 | 戦略を自分の状況に当てはめる |
| 『論語』 | 人間関係の悩みへの助言 |
| 『星の王子さま』 | 場面と自分の体験を重ねて対話する |

人は承認・修正するだけでよい。看板となる重要な作品だけ丁寧に見て、それ以外は提案をそのまま採用する運用も可能。

### ③ 実際の質問ログから見つける

運用開始後、うまく答えられなかった質問を分類し、足りない部品を見つける（「ホームズに仕事の相談をする人が多いが、方法カードがなく答えが浅い」など）。そこから特徴パッケージや本ごとのカードを足す。

## 6. 特徴パッケージがなくても答えられないわけではない

先生は本文検索・章の全文・階層要約という共通の道具を持つため、専用カードがない使い方でもある程度は答えられる。専用カードは「答えられるようにする」ものではなく、**答えの網羅性と根拠の確かさを上げる** もの。

| | 例: ホームズに仕事の相談 |
|---|---|
| カードなし | ホームズの台詞を本文検索で数件見つけ、それを元に答える |
| カードあり | 全事件から方法を体系的に選び、構造の似た事件を根拠付きで示す |

したがって、まず共通の土台で全ジャンルを受け、使われ方を見ながらパッケージを足す順番でよい。

有名作品ほど LLM が元から内容を知っており、本に書いていないことを記憶で答えてしまう危険がある。引用の検証（引用文が実際にその本・その翻訳に存在するか）はこの対策にもなる。

## 7. パイプラインへの反映

```
[0] Intake
[0.5] Profile ──► 特徴の組み合わせ（確信度付き）── 低確信度は人が確認
   │                       │
   │            有効な特徴パッケージを読み込む
   ▼                       ▼
[1] Extract（レイアウト特徴で抽出方法を選択）
[2][3] Normalize / Structure（共通）
[3.5] Tables / Pages（共通）
[4] Chunk / [5] Enrich / 階層要約（共通）
[5.x] 特徴パッケージの処理段（Units, Narrative, Geo, Series …）
[5.9] Re-profile ──► 本文全体の処理結果から特徴を追加 → 必要なパッケージの段だけ追加実行
[5.95] 使い方の提案（LLM）── 人が承認
[6] Index / [7] QA（共通 + パッケージのチェック）/ [8] Publish
```

各段のキャッシュキー（[02](02-ingestion-mvp-validation.md) で実装）には、有効な特徴パッケージとそのバージョンを含める。パッケージを追加・更新したときは、そのパッケージの段以降だけ再実行する。

## 8. 進め方

1. 共通の土台を先に完成させる（[4] Chunk、[6] Index、階層要約、根拠の検証）。これだけでどの本も要約・解説・質問応答（出典付き）が動く。
2. 特徴パッケージの仕組み（定義の読み込み、依存関係、キャッシュキーへの反映）と Profile 段を作る。
3. 最初のパッケージは、効果の大きい `principles`（技術書）と `narrative`（文学の基本）の 2 つ。
4. 以降は、質問ログと要望に応じて追加する。
