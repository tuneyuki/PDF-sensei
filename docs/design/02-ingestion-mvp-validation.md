# 02. 入稿パイプライン MVP 前半の実装と検証（Pro Git）

[01 の設計](01-data-model-and-ingestion.md)のうち **[0] Intake → [1] Extract → [2] Normalize → [3] Structure → Canonical 出力 → [7] QA** を実装し、同一書籍の EPUB と PDF を突き合わせて抽出品質を測った。

## 1. 検証題材

**Pro Git 第2版**（Scott Chacon, Ben Straub / CC BY-NC-SA 3.0）。同じ内容の EPUB と PDF が日本語版・英語版でそろっているため、構造が明示された EPUB を正解として PDF 抽出を評価できる。

| ファイル | 内容 |
|---|---|
| `ja-progit.epub` / `ja-progit.pdf` | 日本語版（progit2-ja、2022-01、PDF 528 ページ） |
| `en-progit.epub` / `en-progit.pdf` | 英語版（progit2、2026-05、PDF 501 ページ） |

入手元: GitHub Releases の `progit/progit2` と `progit/progit2-ja`。書籍ファイルはリポジトリに入れない（`.gitignore` で除外）。

## 2. 実装したもの

```
src/sensei/
  model.py          Canonical（DocTree）スキーマ（pydantic）
  intake.py         [0] SHA-256・形式判定・DRM/暗号化検知
  extract/epub.py   [1] EPUB: OPF → nav/ncx → spine 順に XHTML を走査
  extract/pdf.py    [1] PDF: PyMuPDF + ヒューリスティック（既定）
  extract/docling_pdf.py [1] PDF: Docling（比較用。未検証、5.4 参照）
  textnorm.py       [2] 和欧混在の行連結・正規化・検索キー
  structure.py      [3] 見出し → 節の木、役割判定、目次との突き合わせ
  render.py         doc.md 出力
  qa.py             [7] 自動品質チェック（ok / review / fail）
  compare.py        2 つの DocTree の突き合わせ（抽出器の評価用）
  pipeline.py, cli.py
```

```bash
sensei ingest book.pdf --out out          # out/{book_id}/v1/{extractor}/ に出力
sensei compare A/doc.json B/doc.json      # 抽出品質の比較レポート
```

出力:

```
out/bk_0f0eb7424d7a/v1/pymupdf/
  manifest.json     段ごとのキャッシュキー・バージョン・QA 結果
  stages/extract.json  抽出器の生出力（RawDoc）
  doc.json          Canonical（book / toc / sections / blocks / assets / stats）
  doc.md            人のレビュー用・LLM への章単位投入用
  qa.json           品質チェック結果
  assets/           図版
```

各段は（入力ハッシュ, 段のバージョン, 正規化規則のバージョン, 設定）をキーにキャッシュし、抽出器や構造化の規則を変えたときは影響する段から再実行する。

### 3.2 EPUB（正解）と PDF の突き合わせ

| 指標 | ja | en |
|---|---:|---:|
| 見出し再現率 L1〜L3（章・節・項） | 100% ※ | 100% |
| 見出し再現率 L4 / L5（本文サイズの小見出し） | 98.4% / 90.5% | 94.4% / 88.9% |
| 見出し適合率（PDF の見出しが EPUB にもある割合） | 98.4% | 99.8% |
| 段落の再現率（空白を無視） | **100%** | **100%** |
| 段落の再現率（空白込み）＝段落境界の一致 | 86.1% | 99.3% |
| 箇条書きの再現率（空白を無視） | 100% | 100% |
| コードの行再現率 | 100% | 100% |
| 章ごとの文字数比（PDF/EPUB） | 0.994〜1.001 | 0.999〜1.004 |

※ ja の L1 再現率は表上 76.9%。差分 3 件は付録の表記ゆれ（EPUB「その他の環境でのGit」、PDF「付録 A: その他の環境でのGit」）で、章としては対応が取れている。

**結論: 体裁の整ったテキスト PDF なら、PyMuPDF とヒューリスティックで EPUB とほぼ同等の Canonical が作れる。** 本文の欠落はなく、章・節の構造もしおりとの照合で正しく復元できた。

## 4. 検証で分かったこと（設計への反映）

### 4.1 見出し階層は「PDF のしおり」で学習するのが有効
- フォントサイズだけでは見出しのレベルが決まらない（書籍ごとにサイズ体系が違う）。
- しおりの各項目を該当ページの大きい文字の行と照合し、**フォントサイズ→レベルの対応を書籍ごとに学習**する方式で、L1〜L3 は再現率・レベル一致とも 100%。
- しおりより深い小見出し（本文と同じサイズの「利点」「The Pros」など）は、「1 行だけの段落・短い・文末記号で終わらない・次が本文」という条件で拾った（再現率 89〜98%）。和書のフォントには太字情報がないことがあり、太字を必須条件にできない。
- しおりのない PDF ではサイズの順位で決めるしかなく、精度は落ちる見込み。QA の `toc_match_rate` と `oversized_leaf_sections` で検知して review に回す。

### 4.2 和欧混在の空白は原理的に一致しない → 検索キーで空白を無視する
- 行末の改行を詰めるか空白にするかで、EPUB と PDF の空白が揺れる（例:「あろう GUI」と「あろうGUI」、「です。 Git」と「です。Git」）。ja で空白込みの一致率が 86% にとどまるのはこのため。
- 対応:
  - 保存用テキストでは、改行の片側が和文なら詰める。和文の句読点の直後の空白は除去する。
  - **検索キー（`search_key`: NFKC・小文字化・空白除去）では空白を無視する。** 全文検索インデックスや引用箇所の照合もこのキーで行う。
- 失敗例として、「和文と和文の間の空白を一律に消す」規則は「山田 太郎」「第1章 需要予測」を壊すため不採用にした（テストで検出）。

### 4.3 英語の行末ハイフンは書籍内の語彙で判定する
- 一律にハイフンを除去すると「fast-forward」が「fastforward」になる。
- **書籍内に連結後の語（例: repository）が出現する場合だけ除去**し、それ以外は残す方式にした。

### 4.4 PDF 固有のノイズ
| ノイズ | 対応 |
|---|---|
| 柱・ノンブル | 余白にあり 3 ページ以上で繰り返す行を除去。ノンブルは `page_label` として保持し、物理ページとは別に引用表示に使う |
| アイコンフォント（注記のアイコン等） | フォント名と私用領域の文字で除外（除外しないと見出しと誤認する） |
| コード中の和文 | 等幅フォントでなくても、コードのサイズ・左端と一致する行はコードとみなす |
| 表のセルを本文と誤認 | 表検出を切ると、セルが見出し 27 件・コード 39 件として混入した。表検出は既定で有効にする |
| 表セル内の字間の空白（「ツリ ーのハッシュ」） | 表セルに限って和文字間の空白を詰める |
| ページまたぎの段落 | 前ページ末が文末記号で終わらず、次ページ先頭が字下げなしなら連結。locator は 2 ページ分持つ |
| 行頭の「-」「*」（`--list` の折り返し等） | 字下げされていない場合は箇条書きとみなさない |

### 4.5 EPUB 固有の注意点
- ZIP 内の日本語ファイル名が UTF-8 フラグなしで格納されていることがある（Pro Git ja）。cp437 として読み直し、NFC で照合する。
- 囲み記事（`aside`）の中の `h2` を本文の見出しとして扱うと節構造が壊れる。コンテナ内の見出しは付属物のタイトルとして扱う。
- 見出しのない spine 文書（扉・ライセンス）は、目次のタイトルで節を立てる。
- 同じ書籍でも版により `epub:type` の付け方が違う（ja はすべて `chapter`）。役割（front/body/back/toc/index）はタイトルの規則と併用して判定する。

### 4.6 役割（role）の判定
- 目次・索引ページはチャンク対象から外す（`role=toc/index`）。英語版 PDF の索引は数十ページあり、検索ノイズになる。
- 扉の書名、前付け（序文・謝辞・ライセンス）、付録は `front`/`back` とする。付録は回答の根拠に使うので、チャンク対象に残す。

## 5. 未解決・次の課題

1. **PDF の囲み記事（注記）** が段落に混ざる（「注記Git の “master” ブランチは…」）。罫線や背景の描画、字下げから `note` を判定する必要がある。
2. **ルビ付き PDF**（和書）は未検証。PDF ではルビが本文の行間に小さな文字として出るため、本文サイズより小さい行を除去する処理が要る。
3. **多段組・縦書き・スキャン PDF** は対象外。抽出器を切り替える前提で、判定（段組検出・テキスト層の有無）だけ先に入れる。
4. **Docling との比較は未実施。** この環境のネットワーク方針で huggingface.co がブロックされ、レイアウトモデルを取得できなかった。抽出器（`--extractor docling`）は実装済み。モデルを取得できる環境で `sensei compare` にかければ同じ指標で比較できる。
5. 体裁の異なる別の書籍（商業出版の和書 PDF など）での検証。今回の 2 冊はどちらも Asciidoctor で組版されており、レイアウトが素直。

## 6. 次のステップ（MVP 後半）

1. **[4] Chunk**: 節の境界を守るチャンク分割（600〜1,200 字）。`role=toc/index` は除外。チャンクに `heading_path` と `page_label` を持たせる。
2. **[6] Index**: PostgreSQL + pgvector + 日本語全文検索。埋め込みモデルは、Pro Git の日本語版を使った検索評価セット（質問→正解の節）で選定する。
3. **[5] Enrich**: 節 → 章 → 書籍の順に階層要約を生成。
4. **評価セット**: EPUB と PDF で同じ質問を投げ、同じ節が引けるかを測る（抽出器の差が検索品質にどう効くかを見る）。
