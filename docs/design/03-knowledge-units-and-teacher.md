# 03. 知識カードと「先生」の設計方針

ユーザーは気に入った書籍を選び、その本の「先生」と会話する。書籍のジャンルは問わない（技術書、ビジネス書、料理本、実用書、旅行雑誌、グルメ雑誌、文学作品など）。
本書では、どのジャンルでも **本の内容に基づいて答え、根拠（どのページの何という記述か）を示せる** ための格納形式・会話の仕組み・入稿処理の方針を定める。

[01](01-data-model-and-ingestion.md) のデータ構造と [02](02-ingestion-mvp-validation.md) で実装した入稿パイプライン前半を土台とする。

## 1. 想定ユースケース

| ユースケース | 例 | 求められる回答 |
|---|---|---|
| 要約・解説 | 「3章を要約して」「この用語はどういう意味？」 | 本文に基づく説明と出典ページ |
| 本の考え方を自分の材料に当てはめる | 自分のコードを貼り「『リーダブルコード』の観点でレビューして」 | 指摘・修正案と、各指摘の根拠となる原則・ページ・原文の引用 |
| 自分の状況に合うものを本から選んでもらう | 料理本に「夏バテなんだけど何かオススメある？」 | 推薦レシピ・調理法と推薦理由、出典ページ、写真 |
| 条件に合う場所を提案してもらう | 旅行雑誌に「東京から日帰りで行ける温泉、海の幸もあったらいいな」 | 推薦エリアと、その中の温泉・飲食店の組み合わせ、アクセス、掲載号とページ |
| 好み・場所・時間で店を探してもらう | グルメ雑誌に「豚骨でこってり、チャーシューは炙りでオススメのお店ある？」「五反田駅にきたんだけど、飲み会の後に開いてるお店」 | 条件に合う店とメニュー、営業時間・駅からの距離、掲載号とページ、情報の時点の注記 |
| 物語の内容を知る | 『戦争と平和』に「どんなストーリーなの？」「ピエールってどういう人物？」 | あらすじ（粒度を選べる）、人物像とその変化、根拠の章と引用。読書中ならネタバレを避ける |
| 物語の方法論を自分の状況に当てはめる | 『シャーロック・ホームズの冒険』に「仕事で困ったことになった。ホームズならどう打開する？」 | 似た構造の事件と、ホームズの方法の紹介（場面・台詞の引用付き）と、ユーザーの状況への当てはめ（推論であると明示） |

2 番目以降のように、ユーザーの質問と本の文章が言葉の上で似ていない（ユーザーのコードと原則の説明文、「夏バテ」とレシピ名）ことが多い。本文チャンクのベクトル検索だけでは当てはまる内容を取りこぼすため、本の内容を **構造化した知識カード** として持ち、条件で引けるようにする。

## 2. 全体構造：共通の土台 + ジャンル別の知識カード

```
┌───────────────────────────────────────────────────────────┐
│ ③ 先生（会話）  LLM が道具を使い分けて答える                   │
│    本文検索 / カード検索（条件で絞る）/ 章の全文 / ページ画像     │
├───────────────────────────────────────────────────────────┤
│ ② 知識カード（ジャンル別）  本の中身を「使える単位」にしたもの    │
│    技術書・ビジネス書: 原則・手法    料理本: レシピ               │
│    旅行雑誌: エリア・スポット    グルメ雑誌: 店・メニュー          │
│    文学: 人物・出来事・事件・方法・名言                          │
│    実用書: 手順    どの本でも: 用語・事例                       │
├───────────────────────────────────────────────────────────┤
│ ① 共通の土台（全書籍）                                        │
│    Canonical の本文ブロック（ページ番号・位置付き）、章・節、      │
│    チャンク、階層要約、ページ画像、表                            │
└───────────────────────────────────────────────────────────┘
```

- **① 共通の土台** は要約・解説・一般的な質問と、すべての出典表示を支える。ジャンルに依存しない。
- **② 知識カード** はジャンルごとに項目を定め、本から取り出した構造化データ。
- **③ 先生** はユースケースごとに処理を作り込まず、共通の道具（§5）を LLM に渡して使い分けさせる。コードレビューも料理の相談も同じ仕組みで答える。

## 3. 格納形式

### 3.1 共通の土台に追加するもの

| 格納するもの | 中身 | 用途 |
|---|---|---|
| ページ画像 | 全ページを画像化。ブロックの bbox と対応付け | 根拠を実物のページ（該当箇所に印）で見せる。表・図を Claude に読み直させる |
| 表 | セル構造（行・列・見出し行）、Markdown、切り出し画像、抽出方法と信頼度 | 表の参照・表示（§6） |
| コード例 | コードブロックに言語と「悪い例／良い例」、どのカードの例かを付与 | 修正案の手本、根拠の提示 |

ページ番号は 2 種類持つ（実装済み）。ユーザーに見せるのは **本に印字されたページ番号**（`page_label`）、画像表示や PDF 内の位置指定には **PDF 上の物理ページ**（`locator.pdf.page`）を使う。

### 3.2 知識カード

全ジャンル共通の外枠と、ジャンル別の中身（`attributes`）に分ける。

```jsonc
{
  "unit_id": "bk_xxx-recipe-042",
  "book_id": "bk_xxx",
  "version": 1,
  "type": "recipe",                 // principle | recipe | procedure | term | case | ...
  "schema_version": "recipe/1",
  "title": "豚しゃぶと夏野菜の梅だれ",
  "summary": "茹でた豚肉と夏野菜を梅だれで和える、さっぱりした一品",
  "attributes": { /* ジャンル別（下記） */ },
  "tags": ["さっぱり", "冷やして", "時短"],
  "evidence": [{ "block_id": "b001195", "page_label": "48", "page": 50 }],
  "assets": ["img-0081"],
  "extraction": { "model": "...", "prompt_version": "...", "reviewed_by": null }
}
```

外枠には、ジャンルを問わず次も持たせる（旅行・グルメ雑誌の検討で必要になった）。

```jsonc
  "relations": [{ "type": "contains", "unit_id": "..." }],  // contains | has_menu | example_of | near
  "as_of": "2025-08",            // 何年何月の情報か（雑誌は発行号、書籍は版）
  "series_id": "ser_xxx",        // 雑誌のシリーズ（号をまたいだ名寄せ用）
  "is_ad": false                 // 広告・タイアップ
```

**属性ごとに出所を区別する。**

```jsonc
"season":   [{ "value": "夏", "source": "book", "evidence": ["b001203"] }],
"benefits": [{ "value": "疲労回復", "source": "book", "evidence": ["b001198"] },
             { "value": "食欲がないときに", "source": "inferred" }],
"location": { "lat": 35.10, "lon": 139.07, "source": "external", "provider": "geocoder-x" }
```

- `source: book` の属性には本文ブロックを必ず紐付ける。出典として本を示せるのはこちらだけ。
- `source: inferred` は LLM の推定（材料の旬から季節を推定した、など）。回答では「一般的な知識による補足」と明示し、本の内容と混ぜない。
- `source: external` は外部データ（住所から求めた緯度経度、乗換案内の所要時間、Web で確認した営業状況など）。提供元を記録し、出典を本とは分けて表示する。
- 根拠として表示するのは常に `evidence` が指す **本文ブロックの原文** であり、LLM が書いた要約文ではない。

### 3.3 ジャンル別スキーマ（初期）

スキーマは登録制とし、`type` ごとに項目・必須項目・検証規則を定義する。後から追加できる。

**principle（技術書・ビジネス書の原則・手法）**

```jsonc
{
  "chapter": "2章 名前に情報を詰め込む",
  "statement": "get や size のような曖昧な語を避け、より具体的な語を選ぶ",
  "rationale": "名前は短いコメント。曖昧だと読み手が推測を強いられる",
  "detect": ["get/do/process/handle 等の汎用動詞だけの関数名", "tmp/retval/foo 等の意味のない変数名"],
  "fix_patterns": ["get → fetch/download/compute など処理内容を表す語へ"],
  "examples": [{ "kind": "bad", "block_id": "b000231" }, { "kind": "good", "block_id": "b000233" }]
}
```

`detect`（当てはまる兆候）は、ユーザーの材料（コード・企画書など）に原則を当てはめるときの手掛かりになる。

**recipe（料理本）**

```jsonc
{
  "category": "主菜",
  "ingredients": [{ "name": "豚ロース薄切り肉", "normalized": "豚肉", "amount": "200g" }],
  "steps": ["…", "…"],
  "time_min": 15,
  "servings": 2,
  "calories": null,
  "season": [{ "value": "夏", "source": "book", "evidence": ["b001203"] }],
  "benefits": [{ "value": "疲労回復", "source": "book", "evidence": ["b001198"] }],
  "tips": [{ "text": "…", "evidence": ["b001201"] }]
}
```

**area / spot（旅行雑誌）**: エリアがスポットを含む（`contains`）。提案はエリア単位で、中のスポットを組み合わせる。

```jsonc
// area
{
  "location": { "pref": "静岡県", "lat": 35.10, "lon": 139.07, "source": "external" },
  "access": [{ "from": "東京駅", "mode": "新幹線", "minutes": 45, "source": "book", "evidence": ["b000812"] }],
  "best_season": [{ "value": "通年", "source": "book", "evidence": ["b000815"] }],
  "model_course": { "evidence": ["b000830"] }
}
// spot
{
  "category": "日帰り温泉",                          // 語彙で正規化（§3.4）
  "features": [{ "value": "露天風呂から海が見える", "source": "book", "evidence": ["b000841"] }],
  "info": { "address": "…", "tel": "…", "price": "1,200円", "source": "book", "evidence": ["b000845"] },
  "hours": { /* 営業時間（下記） */ },
  "period": null                                     // イベント・見頃などの期間
}
```

**shop / menu（グルメ雑誌）**: 店がメニューを持つ（`has_menu`）。

```jsonc
// shop
{
  "station": [{ "name": "五反田", "walk_min": 3, "source": "book", "evidence": ["b0412"] }],
  "hours": { /* 営業時間（下記） */ },
  "awards": [{ "value": "読者投票 総合3位", "source": "book", "evidence": ["b0409"] }]
}
// menu
{
  "soup_base": ["豚骨"],
  "richness": { "value": 4, "scale": 5, "source": "book", "evidence": ["b0415"] },
  "toppings": [{ "raw": "バーナーで炙ったチャーシュー", "normalized": "炙りチャーシュー", "source": "book" }],
  "noodle": "極太ストレート",
  "price": 1100
}
```

**営業時間**（spot・shop 共通）: 誌面の表記（`raw`）を残し、判定用の構造化データに変換する。深夜営業は 24 時を超える表記（翌 2:00 → 26:00）で持つ。「不定休」「売り切れ次第終了」など確定できない情報には `uncertain` を立てる。

```jsonc
"hours": {
  "raw": "11:00〜翌2:00（L.O.1:30）、日祝〜22:00、水曜休",
  "schedule": [
    { "days": ["月","火","木","金","土"], "open": "11:00", "close": "26:00", "last_order": "25:30" },
    { "days": ["日","祝"], "open": "11:00", "close": "22:00" }
  ],
  "closed": ["水"],
  "uncertain": false,
  "source": "book", "evidence": ["b0418"]
}
```

**character / event（文学作品）**: 人物は別名の統合と、物語の中での変化（arc）を持つ。出来事は物語上の順序（`story_order`）を持つ。

```jsonc
// character
{
  "aliases": ["ピエール", "ピョートル・キリーロヴィチ", "ベズーホフ伯爵", "Pierre"],
  "profile": [{ "value": "ベズーホフ老伯爵の庶子。のちに莫大な遺産を継ぐ", "source": "book", "evidence": ["b00412"], "revealed_at": "1-1-6" }],
  "relations": [{ "to": "char-natasha", "type": "後の妻", "revealed_at": "4-4-20" },
                { "to": "char-andrei", "type": "親友", "revealed_at": "1-1-2" }],
  "arc": [{ "when": "第1巻", "summary": "社交界になじめない青年", "evidence": ["…"] },
          { "when": "第4巻", "summary": "捕虜生活を経て内面が変わる", "evidence": ["…"] }],
  "first_appearance": { "chapter": "1-1-2", "evidence": ["b00398"] },
  "key_quotes": [{ "text": "…", "evidence": ["b0xxxx"] }]
}
// event
{ "story_order": 412, "chapter": "1-3-12", "participants": ["char-andrei"], "place": "place-austerlitz",
  "summary": "…", "evidence": ["…"] }
```

`revealed_at`（その情報が明かされる章）を属性ごとに持たせ、ネタバレ回避（§4.1 のユーザーの文脈）に使う。

**case / method（推理小説などの方法論）**: 事件ごとの「問題 → 手掛かり → アプローチ → 転機 → 解決」と、作品を横断する方法（ホームズの推理法など）。方法カードは、実際に使われた場面と台詞を根拠に持つ。

```jsonc
// case（各短編）
{ "problem": "…", "client": "…", "clues": [{ "text": "…", "evidence": ["…"] }],
  "approach": [{ "method": "method-observation", "how": "…", "evidence": ["…"] }],
  "turning_point": { "summary": "…", "evidence": ["…"] }, "resolution": "…" }
// method（作品横断）
{ "statement": "データが揃う前に理論を立てない", "when_to_use": "…",
  "applied_in": [{ "case": "case-bohemia", "evidence": ["…"] }],
  "quotes": [{ "text": "…", "evidence": ["…"] }] }
```

ほかに **place（場所）**、**theme（テーマ・モチーフ）**、**quote（名言）** を持つ。

**procedure（実用書の手順）**、**term（用語）**、**case（事例）** も同じ外枠で定義する。

### 3.4 Index 層（PostgreSQL）

[01](01-data-model-and-ingestion.md) の `concepts` テーブルを知識カードに置き換える。

```sql
CREATE TABLE units (
  unit_id        text PRIMARY KEY,
  book_id        text,
  version        int,
  type           text,             -- principle | recipe | procedure | term | case
  schema_version text,
  title          text,
  summary        text,
  attributes     jsonb,            -- ジャンル別の中身
  facets         jsonb,            -- 条件検索用に正規化した値（season, ingredients, category, soup_base...）
  tags           text[],
  evidence       jsonb,            -- [{block_id, page_label, page}]
  relations      jsonb,            -- [{type, unit_id}]
  as_of          text,             -- 情報の時点（号・版）
  series_id      text,             -- 雑誌のシリーズ
  is_ad          boolean DEFAULT false,
  geom           geography(Point), -- 位置（PostGIS。距離・駅からの近さの検索用）
  hours          jsonb,            -- 営業時間の構造化データ
  embedding      vector(1024),     -- title + summary + 主要属性
  search_text    text,             -- 全文検索用（NFKC・空白除去は search_key と同じ規則）
  reviewed       boolean DEFAULT false
);
CREATE INDEX ON units USING gin (facets jsonb_path_ops);
CREATE INDEX ON units USING gin (tags);
CREATE INDEX ON units USING hnsw (embedding vector_cosine_ops);
```

材料名などの表記ゆれは正規化辞書で吸収し、元の表記（`name`）と正規化名（`normalized`）を両方持つ。旬の食材表などの外部知識は、書籍とは別のデータとして管理し、回答では一般知識として扱う。

**ジャンル別の語彙（分類表）** をスキーマと一緒に登録する。例: ラーメンのスープの種類（豚骨・醤油・味噌・塩・鶏白湯…）、トッピング（「バーナーで炙った」「焦がし」→ 炙りチャーシュー）、料理の分類、旅行のスポット種別（日帰り温泉・海鮮・景勝地…）。語彙に正規化した値を条件検索に使い、元の表現は残して意味検索で拾う。

同じスポット・店が複数の号に載る場合は、シリーズ単位で名寄せ（名前・住所・電話番号）し、新しい号の情報を優先する。古い号の記述は履歴として残す。

## 4. 会話の仕組み

### 4.1 先生に渡す道具

| 道具 | 内容 |
|---|---|
| `search_text(query)` | 本文チャンクのハイブリッド検索（ベクトル + 全文） |
| `search_units(type, filters, query)` | 知識カードの検索。条件（季節・材料・カテゴリ等）と意味の両方で絞る |
| `list_units(type)` | カードの一覧（原則を全件照らし合わせるレビュー等で使う） |
| `get_unit(unit_id)` | カード 1 件と根拠ブロックの原文 |
| `get_section(section_id)` | 章・節の全文（要約・詳しい解説用） |
| `get_page_image(page, bbox?)` | ページ画像（表・図・地図の確認、根拠の表示） |
| `search_nearby(point or station, radius)` | 位置・駅からの距離での絞り込み |
| `is_open(unit_id, datetime)` | 営業時間・会期の判定（定休日・祝日・深夜営業・不確定を考慮） |

先生には **ユーザーの文脈**（現在の日時、許可があれば現在地、文学作品なら読んでいる位置）も渡す。読んでいる位置が分かっている場合は、`revealed_at` がそれより後の情報を伏せて答える（ネタバレ回避）。「今」「飲み会の後」「来月」のような時間の言い方を、具体的な日時の条件に解釈し、その前提を回答に書く。

先生の人格（口調・ジャンルの前提）は書籍ごとのプロンプトで与える。どの道具をどう使うかは LLM に任せ、ユースケースごとの固定処理は作らない。

### 4.2 共通の回答手順

```
① 質問の分解: 依頼の種類（要約／解説／当てはめ／推薦）と、
   ユーザーの状況を本の言葉・条件に言い換える
② 検索: 条件で絞る（カード）/ 意味で探す（カード・本文）/ 語句で探す（全文）
③ 候補の選定と理由付け: 本の記述を優先。一般知識の補足はそうと分かるように書く
④ 根拠の取得: 選んだカード・本文の根拠ブロック（原文・ページ）
⑤ 回答の作成
⑥ 根拠の検証: 引用文が元ブロックに実在するか（search_key で照合）、
   ページ番号がブロックの page_label と一致するかを機械的に確認。
   合わない根拠は直させるか消す
```

根拠の受け渡しには Claude API の引用機能（Citations: 渡した文書のどこを根拠にしたかを回答と一緒に返す）の利用を検討する。根拠ブロックを文書として渡せば、引用箇所がブロック単位で返り、ページ番号・位置へ機械的に変換できる。詳細は実装時に確認する。

### 4.3 例 1: コードレビュー（『リーダブルコード』）

```
ユーザー: 自分のコード + 「リーダブルコードの観点でレビューして」
  ① 依頼 = 当てはめ（レビュー）
  ② list_units(principle) で原則カードを全件取得（プロンプトキャッシュで常駐）
  ③ コードの気になる箇所を行番号付きで洗い出し、各箇所に当てはまる原則を選ぶ
  ④ get_unit で根拠ブロック（原文・ページ）と悪い例・良い例を取得
  ⑤ 指摘・修正案コード・根拠（章・ページ・原文の短い引用）を書く
  ⑥ 引用とページを検証
```

原則カードは 1 冊で 100〜150 件・数万トークン程度に収まる見込みのため、検索ではなく **全件をプロンプトに入れて** 照らし合わせる（ユーザーのコードと原則の説明文は言葉が似ておらず、検索だと取りこぼすため）。複数書籍を扱う規模になったら、カードの `detect` を検索対象にする方式に切り替える。

回答イメージ:

> **指摘1（12行目）`def get_data(tmp):`**
> 関数名 `get` が曖昧で、ネットワークから取るのかキャッシュを読むのかが分からない。
> 修正案: `def fetch_user_profile(user_id):`
> 根拠: 2章「明確な単語を選ぶ」p.10「（原文の短い引用）」［ページを表示］

### 4.6 例 4: 店探し（グルメ雑誌）

**好みで探す**: 「豚骨でこってり、チャーシューは炙りでオススメのお店ある？」

```
  ① 豚骨（必須）・こってり（必須寄り）・炙りチャーシュー（希望）に分解
  ② search_units(menu, {soup_base: 豚骨, richness >= 4, toppings: 炙りチャーシュー})
     語彙に当てはまらない特徴は意味検索で補う
  ③ 誌面のランキング・大賞・編集部イチオシ（awards）を推薦の根拠として優先
  ④〜⑥ 店・メニューの根拠ブロックと写真を取得し、回答作成・検証
```

**場所と時間で探す**: 「五反田駅にきたんだけど、飲み会の後に開いてるお店」

```
  ① 「飲み会の後」を「今日の 22〜24 時ごろ」と解釈（前提を回答に書く）
  ② search_nearby(station: 五反田, 徒歩 10 分程度)
     × is_open(その時間帯)  × 今日が定休日でない
     駅からの徒歩分数は誌面の記載を優先し、なければ住所からの計算値（external）
  ③〜⑥ 候補の順位付け、根拠取得、回答作成・検証
```

回答イメージ:

> 22時以降に開いているお店を探しました。
> **○○家**（五反田駅から徒歩3分、深夜2時まで・L.O.1:30）特製豚骨ラーメン 1,100円（p.58）
>
> 出典: 『ラーメンWalker東京2026』。掲載時点の情報です。営業時間は変わりやすいので、出発前にご確認ください。

グルメ情報は旅行情報よりさらに変わりやすい（閉店・移転・営業時間の変更）。雑誌の情報だけで「今開いている」と断言しない。回答には必ず掲載号と「掲載時点の情報」の注記を付ける。より確実にするには、回答時に Web や地図サービスで営業状況を確認する（結果は `external` として出典を分ける）。

### 4.7 例 5: 物語の内容（『戦争と平和』）

**「どんなストーリーなの？」**: 入稿時に作った階層要約（章 → 編 → 巻 → 作品全体）を使う。まず作品全体のあらすじで答え、「アウステルリッツの戦いのあたりを詳しく」のような質問には該当する巻・章の要約まで降りる。出典は要約文ではなく、要約の元になった章（第1巻第3編第12章など）を示す。

**「ピエールってどういう人物？」**

```
  ① 人物名を別名表で解決（ピエール = ピョートル・キリーロヴィチ = ベズーホフ伯爵）
  ② get_unit(character) で人物カード（人物像・関係・変化・初登場・名言）
  ③ 読んでいる位置が分かっていれば、それより後に明かされる情報を除外
  ④ 根拠の場面（章）と引用を取得 → ⑤ 回答作成 → ⑥ 引用の検証
```

人物は物語の中で変わるため、一言の説明で済ませず、巻ごとの変化（arc）として答える。

### 4.8 例 6: 物語の方法論の当てはめ（『シャーロック・ホームズの冒険』）

**「仕事で困ったことになった。ホームズならどう打開する？」**: 知識を探すだけでは答えられず、物語から取り出した方法論をユーザーの状況に当てはめる応用。コードレビュー（原則をコードに当てはめる）と同じ構造で扱う。

```
  ① ユーザーの状況を構造で捉える（何が分かっていて、何が不明か、誰が関係するか）
  ② 構造の似た事件カードと、使えそうな方法カードを選ぶ
  ③ ホームズならどう考えるかを、具体的な打ち手として書く
  ④ 事件・方法の根拠となる場面と台詞を取得 → ⑤ 回答作成 → ⑥ 引用の検証
```

回答では次を区別する。

- **本の内容**: 「『ボヘミアの醜聞』でホームズは…した（第○章）」という場面の紹介と台詞の引用。引用は原文と照合して検証する。
- **当てはめ**: ユーザーの仕事への適用は LLM の推論であり、そうと分かる書き方をする。

ホームズの口調で語らせる演出（ロールプレイ）も可能とするが、**本に存在しない文章をホームズの台詞として引用の体裁で出さない**ことを規則とする（引用の検証で機械的に防ぐ）。

旅行・グルメ雑誌は誌面がもっとも複雑なジャンル。

| 難しさ | 対策 |
|---|---|

| スポット・店の情報欄（住所・電話・営業時間・料金・アクセス） | 形が決まった欄なので項目を決めて抽出。抽出後に住所・電話番号・営業時間の形式をチェック |
| アイコンやゲージ（「こってり度 ●●●●○」「スープ：豚骨」） | 文字データでは取れないため、画像からの読み取りが必須 |
| 地図 | 画像として保存し、エリアカードに紐付けて表示（地図から位置を読み取ることまではしない） |
| 広告ページ・タイアップ記事 | ページ単位で広告か判定し、ページの役割に `ad` を追加。カードは `is_ad` |
| 号をまたぐ重複 | [5.7] でシリーズ単位に名寄せ |

| 難しさ | 対策 |
|---|---|
| 長大（『戦争と平和』は数千ページ・数百万字）で一度にプロンプトに入らない | 階層要約（章 → 編 → 巻 → 作品）と、章ごとの並列抽出 → 統合（[5.8]） |

| 同じ作品の複数の翻訳 | 翻訳が違えば別の本として扱う。引用はその翻訳の文章のまま |
| 入稿時の LLM 処理量（全章を通す） | 章ごとに並列処理し、Batch API で費用を抑える |

## 6. 表の読み取り方針

PDF に文字データがあり罫線のある単純な表なら、現状の抽出でほぼ読める（Pro Git ja の 6 表は内容が正しく取れた）。弱点は、結合セル・複数段の見出し行・罫線のない表・スキャン PDF。

1 つの方法に頼らず 3 段構えにする。

1. **検出**: 表の範囲を見つけ、行・列の構造で取り出す（PyMuPDF `find_tables`）。
2. **自動検査**: 次の観点で信頼度を付ける。
   - 表の範囲内のページ文字が、セルにどれだけ入ったか（被覆率）
   - 空セルの割合
   - 行ごとの列数のそろい具合
3. **作り直し**: 信頼度が低い表は、切り出した画像を Claude に読ませて構造化データとして作り直す。それでも怪しいものは人が確認する。

どの方法で抽出しても **表部分の画像は必ず残す**。回答時に元の表を画像で示せ、必要なら回答時に原画像を読み直させられる。

## 7. 方針として決めたこと

- ジャンルに依存しない共通の土台と、ジャンル別の知識カードの 2 層で持つ。
- カードの属性は「本に書いてある（出典付き）」「推定」「外部データ」を区別し、本の出典として示すのは前者の原文だけ。
- 回答の根拠は機械的に検証する（引用の実在、ページ番号の一致）。
- すべてのカードに情報の時点（版・号）を持たせ、変わりやすい情報（営業時間・料金）には掲載時点である旨を必ず添える。
- 位置・時間・語彙・カード間の関係・名寄せは、特定ジャンル専用ではなく共通の仕組みとして持つ。
- ロールプレイ（登場人物の口調で答える）をしても、本に存在しない文章を引用の体裁で出さない。
- 当てはめ・提案（ユーザーの状況への適用）は LLM の推論として、本の内容と区別して書く。
- 先生は共通の道具を使い分ける。ユースケースごとの固定処理は作らない。
- 表と図は、構造化データと画像の両方を残す。

## 8. 未決事項

1. **最初に対応するジャンル。** 技術書（実装済みの土台がそのまま使える）と料理本の 2 つから始める案。料理本は検証用のファイル（PDF/EPUB）が必要。
2. **一般知識での補足を許すか。** 本に書いていないこと（例: 夏バテにビタミン B1 が効く）を補足として出すか、本の内容だけに限定するか。
3. **回答に載せる本文の量。** 個人利用なら作り方の全文も可。複数人で共有するサービスなら、要約とページ番号の提示までに留めるのが無難。
4. **カードの人手確認を入れるか。** → [09](09-review-strategy.md) で方針を決定。全件は見ず、例外キュー・抜き取り検査・質問テストで本（版）単位に受け入れを判定する。
5. **根拠の見せ方。** テキストの引用だけか、ページ画像に印を付けて表示する画面まで作るか。
6. **外部サービスとの連携を許すか。** 位置・移動時間・駅からの距離の計算には地図・乗換案内のサービスが必要。使わない場合は誌面のアクセス情報だけで答え、記載のないものは「アクセス不明」とする。
7. **最新情報の確認。** 掲載時点の情報と注記するだけか、回答時に Web 等で営業状況を確認する機能まで作るか。
8. **広告の扱い。** 推薦から外すか、「PR」と明示して候補に含めるか。
9. **現在地を使うか。** 駅名などを言ってもらえば位置情報なしでも答えられる。GPS 等の現在地まで使うか。
10. **検証用の雑誌。** 旅行・グルメ雑誌は誌面がもっとも複雑なため、実物で抽出を試さないと精度が読めない。
11. **ネタバレ回避を入れるか。** 入れる場合は、ユーザーが読んでいる位置を伝えられる仕組み（UI）が必要。
12. **ロールプレイを許すか。** 許す場合も、存在しない台詞を引用として出さない規則は守る。
13. **翻訳の扱い。** 1 作品につき 1 つの翻訳でよいか、複数の翻訳や原文を並べて扱うか。
    検証素材について: トルストイもコナン・ドイルも原作の著作権は切れているが、日本語訳には翻訳者の権利が残っている場合がある。検証には英語の原文・英訳（Project Gutenberg）や、権利が切れているか自由なライセンスの付いた翻訳（青空文庫など。作品ごとに条件を確認）を使う。

## 9. 次のステップ

1. 共通の土台の残り: [4] Chunk → [6] Index（PostgreSQL + pgvector + 日本語全文検索）→ 検索の評価セット（Pro Git ja）。
2. ページ画像の作成と表の自動検査。
3. 知識カードの外枠とスキーマ・語彙の登録の仕組み、principle と recipe の 2 スキーマ。
4. 先生の道具（§4.1）と根拠検証の実装。
5. 雑誌向け: ページ画像を読ませる抽出、営業時間の構造化と `is_open`、位置・距離（PostGIS）、シリーズの名寄せ。
6. 文学向け: 階層要約、章ごとの人物・出来事の抽出と別名の統合、`revealed_at` によるネタバレ回避、事件・方法カード。
