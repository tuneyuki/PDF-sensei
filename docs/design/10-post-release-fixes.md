# 10. 公開後の修正と版の運用

商用公開後に内容の誤りが見つかったとき、どう直して本番に反映するかを定める。前提は次のとおり。

- ステージングの DB で入稿・確認し、本番の DB には書籍（版）単位で昇格する。LLM の出力は成果物として保存されており、昇格で LLM は再実行しない（[09](09-review-strategy.md) §6）。
- レビューは「人はレコードではなく仕組みを直す」方針で行い、個別の修正は `overrides.json`（上書き）として成果物に残す（[09](09-review-strategy.md) §5）。

## 1. 基本方針: 緊急度と影響範囲で経路を分ける

すべての修正を「入稿し直し → レビュー → 昇格」の経路に流すと、急ぎの修正に間に合わず、軽い修正にも手間がかかりすぎる。修正を 4 種類に分け、それぞれの経路を決める。

| 種類 | きっかけの例 | 経路 | 反映まで | LLM 代 | 再レビューの範囲 |
|---|---|---|---|---|---|
| **① 止める** | 誤った情報・ネタバレ事故・権利の申し立て | 該当するカード・チャンク・本を検索対象から外す（削除しない） | 数分 | 0 | 事後に原因を調べる |
| **② 個別に直す** | 特定のカードの誤り、表記の誤り | `overrides.json` に修正を追加し、登録し直す | 数時間〜1 日 | 0 | 直したものだけ |
| **③ 仕組みを直す** | 同じ種類の誤りが複数の本にある | プロンプト・規則を直し、影響する本の段を再実行して新しい版を作る | 数日〜 | 再実行した段ぶん | 前の版との差分 |
| **④ 原本が変わる** | 改訂版・正誤表の反映 | 新しい原本を同じ本の新しい版として入稿する | 数日〜 | 全段ぶん | 前の版との差分 |

①で被害を止めてから、②〜④で直す、という順に組み合わせて使う。

## 2. ① 止める

### 2.1 止める単位

| 単位 | 方法 | 用途 |
|---|---|---|
| 本 | 公開中の版を外す（`books.active_version` を外す） | 権利の申し立て、本全体の重大な誤り |
| カード | 上書きの一種（`suppress`）で検索・道具の対象から外す | 特定のカードの誤り・ネタバレ |
| チャンク | 同上。本文検索の対象から外す | 特定の箇所の誤抽出・不適切な内容 |

いずれも **データは削除せず、対象から外すだけ** にする。原因の調査、巻き戻し、いつから止めたかの説明に使うため。

### 2.2 成果物と本番 DB に同時に反映する

[09](09-review-strategy.md) では「DB を直接書き換えない」としたが、緊急時は昇格の手順を待てない。そこで ① は **「`overrides.json` への記録」と「本番 DB への反映」を必ず 1 つの操作で同時に行う** 専用の操作とする。

- 成果物に記録されるため、あとで登録し直しても止めた状態が保たれる。
- ステージング DB にも同じ操作を反映し、環境間で状態をそろえる。
- この操作は LLM も埋め込みも使わず、入稿のやり直しも不要。

### 2.3 止めたあと

止めた対象は例外キュー（[09](09-review-strategy.md) §3.1）に入れ、原因を調べて ②〜④ のどれで直すかを決める。原因が仕組み（プロンプト・規則）にある場合は、同じ誤りが他の本にもないかを確かめる（§4.1）。

## 3. ② 個別に直す

1. `overrides.json` に修正を追加する（カードの項目の修正、承認・却下）。
2. ステージング DB に登録し直し（`sensei index`）、直した箇所と、その本の質問テストを確かめる。
3. 本番 DB に書籍単位で昇格する。

LLM は使わない。登録し直しでは埋め込みが再計算されるが、額は小さい（[08](08-mvp1-corpus-and-ingest-cost.md)）。登録は版単位で 1 トランザクションで行うため、利用者に半端な状態は見えない。

急ぐ場合は ① で止めてから ② を通常の手順で行う。② をステージングを経ずに本番へ直接入れる経路は作らない。

## 4. ③ 仕組みを直す

### 4.1 影響する本を特定する

各段の成果物の `manifest.json` には、キャッシュキーとして段のバージョン・モデル名・プロンプトのバージョンが記録される（[09](09-review-strategy.md) §6）。これを集計すれば、**直したいプロンプト・規則で作られた本（版）の一覧** が得られる。この一覧を再実行の対象にする。

### 4.2 流れ

1. プロンプト・規則を直し、段のバージョン（またはプロンプトのバージョン）を上げる。
2. 対象の本ごとに新しい版を作る。キャッシュにより、直した段から後ろだけが再実行される。
3. ステージングで差分レビュー（§6.2）と質問テストを行い、受け入れを判定する。
4. 合格した版を本番に書籍単位で昇格し、公開中の版を切り替える。

### 4.3 費用

再実行した段の LLM 代がかかる（[08](08-mvp1-corpus-and-ingest-cost.md) の段ごとの目安 × 対象の本の数）。プロンプトの調整は少数の本で行い、固まってから対象の全冊を 1 回流す。

## 5. ④ 原本が変わる

改訂版・正誤表の反映など、原本ファイルが変わる場合は、**同じ本の新しい版** として入稿する（§8 で `book_id` の扱いを見直したうえで）。以降は ③ と同じく、差分レビュー → 昇格 → 切り替えの順に進める。

原本が変わると抽出からやり直すため、全段の LLM 代がかかる。ブロックの対応も変わりうるため、上書きの持ち越し（§6.3）で例外が多めに出る。

## 6. 共通の仕組み

### 6.1 版の状態と、切り替え・巻き戻し

| 状態 | 意味 |
|---|---|
| `indexed` | 登録済み・未公開 |
| `accepted` | 受け入れ判定に合格（[09](09-review-strategy.md) §4）。昇格・公開の対象 |
| `active` | 公開中（本ごとに 1 つ） |
| `archived` | 以前の公開版。巻き戻し先として残す |

- 現在の実装は、新しい版を公開すると前の版を `archived` にするが、**行は削除しない**（`store.py` の `_activate`）。前の版を指定して公開し直せば即座に巻き戻せる。この性質を運用の前提とする。
- 公開後しばらく（期間は §10）は前の版を削除しない。
- 現在の実装の状態は `indexed` / `active` / `archived` の 3 つ。`accepted` は受け入れ判定の実装（[09](09-review-strategy.md) §8）と合わせて追加する。

### 6.2 差分のレビュー

新しい版を一から [09](09-review-strategy.md) の手順でレビューするのではなく、**前の版から何が変わったか** だけを見る。

- カードの追加・削除・変更の一覧（変わらなかったカードは見ない）
- 質問テストで答えが変わった質問（良くなったもの・悪くなったもの）
- 例外キューに新しく出たもの

### 6.3 上書きの持ち越し

新しい版を作るときは、前の版の上書き（② の修正、① の停止）を新しい版に引き継ぐ。根拠ブロックなど再実行しても変わりにくい手掛かりで対応を取り、対応が取れなかったものは例外キューに出す。

**引き継ぎ漏れは、直したはずの誤りが新しい版で復活する事故になる。** 公開を切り替える前に、前の版のすべての上書きについて「引き継いだ／不要になった（理由付き）」のどちらかになっていることを確認する。

### 6.4 変更の記録

誰が・いつ・何を・なぜ変えたかを残す。

- `overrides.json` の変更履歴（Cloud Storage のオブジェクトのバージョン管理、または Git での管理）。各上書きには理由と実施者を書く。
- 版の公開・巻き戻し・停止の履歴（DB に操作ログのテーブルを置く）。

権利の申し立てなどに対応するとき、いつから止めたか、何を変えたかを示せるようにする。

## 7. 実装上の約束

[09](09-review-strategy.md) §6 に加えて、次を守る。

1. **①（止める）は成果物と DB に同時に反映する 1 つの操作として作る。** DB だけを書き換える手段は用意しない。
2. **公開の切り替えは版単位で、前の版を残す。** 巻き戻しは「前の版を公開する」操作で行う。
3. **新しい版を公開する前に、上書きの持ち越しを確認する**（§6.3）。確認が済んでいない版は公開できないようにする。

## 8. 書籍の ID の見直し

### 8.1 問題

現在の実装は `book_id` を **原本ファイルの SHA-256 から作っている**（`intake.py`、`"bk_" + sha256[:12]`）。同じファイルならどの環境でも同じ ID になるため、書籍単位の昇格には都合がよい。

一方、④ では原本が変わるとハッシュが変わり、**別の本として扱われる**。その結果、次がすべて切れる。

- 上書きの持ち越し（前の版の修正が新しい版に引き継げない）
- 利用コンテンツ（シリーズ）への所属
- 利用者の会話履歴との対応

### 8.2 方針: 元の設計に戻す

[01](01-data-model-and-ingestion.md) §2.2 の設計では、`book_id` は ULID で、`version` は「同一書籍の再入稿・改訂で増える」としていた。ハッシュ由来の ID は [02](02-ingestion-mvp-validation.md) の実装で入った暫定のもので、本格サービスでは元の設計に戻す。

| | 役割 | 決まり方 |
|---|---|---|
| `book_id` | 作品としての同一性 | 初回の入稿で一度だけ発行する（ULID）。以降の改訂版は同じ `book_id` の新しい版として入稿する |
| `book_versions.source_sha256` | 原本ファイルの同一性 | 版ごとに持つ（既存の列）。重複入稿の検知に使う |
| ISBN | 作品の手掛かり | 入稿時に既存の本の候補を示すのに使う。ISBN のない本もあるため ID にはしない |

- 入稿に「既存の `book_id` を指定して新しい版として登録する」指定を設ける。
- 同じハッシュの原本が既に入稿済みなら、その旨を知らせる（重複入稿の防止）。
- `book_id` は **ステージングでの初回入稿時に発行し、成果物（`doc.json`）に記録して運ぶ**。本番では発行し直さない。これで書籍単位の昇格でも環境間で ID がそろう。

## 9. 公開中の会話との整合

利用者の過去の会話には、前の版のページ番号や引用が残っている。版を切り替えたあとも過去の会話の引用を表示できるようにする。

- 回答の引用は `(book_id, version, block_id)` の組で記録する。版を含めることで、切り替え後も元の版の原文を引ける。
- `archived` の版のブロックは、会話履歴の保持期間が過ぎるまで削除しない。
- ① で止めた内容は、過去の会話の表示でも隠すかどうかを決める（権利の申し立ての場合は隠す必要がある）。

## 10. 未決事項

1. **前の版を残す期間。** 巻き戻しのためには数週間、会話履歴の表示のためには履歴の保持期間と同じだけ必要。
2. **① を実行できる人。** 運用担当者がすぐに実行できる必要がある一方、誤操作の影響が大きい。権限と、実行後の確認の手順。
3. **緊急度ごとの対応時間の目標。** たとえば「権利の申し立ては受け付けから○時間以内に①」。
4. **利用者への告知。** 内容を直したことを利用者に知らせるか（直した本の画面に「○月○日に内容を更新」と出す、など）。
5. **止めた内容を過去の会話の表示でも隠すか。** 申し立ての種類によって分けるか。
